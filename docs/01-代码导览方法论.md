# 01 · 代码导览方法论（脱敏示例）

> 核验日期：2026-11-11
> 定位：本文件沉淀的是对一个多平台运动数据同步客户端做静态梳理时形成的**分析方法与职责骨架**。具体类名、包路径、文件计数、行号锚点与数据库表结构细节已按脱敏要求隐去，不构成对任何具体反编译包的还原；可复用的是分层思路、调用链骨架与定位方法。

## 一、职责分层（六层骨架）

同类多平台同步客户端通常可按职责聚成六层，梳理时先分层再下钻，避免被海量界面类淹没：

| 层 | 职责一句话 | 典型内容 |
|---|---|---|
| 平台客户端层 | 各运动平台的鉴权、列表、下载、上传调用 | 按平台组织的客户端组件；统一上传路由；上传结果模型（成功 / 跳过 / 待入库） |
| 模型枚举层 | 平台枚举、活动记录、同步任务、平台能力矩阵、文件种类 | 平台 short 名即缓存与记忆键；活动模型含 id、平台、开始时间、类型、标题、距离、时长、附加信息 |
| 本地状态与数据修补层 | 凭证与设置存取、活动缓存、FIT 时间 / 坐标 / 清洗修补、GPX 时间修补 | 键值库与本地缓存库；FIT 构造与设备伪装；坐标纠偏；时间归一化 |
| 界面层 | 登录、同步、列表、详情、合并预览等界面与交互桥 | 界面组件、WebView 登录页与脚本注入、预览画布 |
| 合并预览层 | 多来源轨迹合并、预览与贴纸类功能 | 合并编排、预览渲染 |
| 应用外壳与后台任务层 | 启动外壳、后台同步任务、前台服务、通知与渠道 | 后台任务调度、前台通知、并发控制、登录态检测 |

## 二、七条核心调用链骨架

下列链路是同类客户端最常出问题的主干；梳理时按骨架逐段核对，不在公开文档中保留具体锚点。

### ① 登录态检测与凭证存取
启动外壳 → 进入主界面 → 逐平台判定凭证是否有效；无效则按平台走刷新或重登（有的平台刷令牌，有的账号密码重登）；仍无效的平台保留或清除凭证，结果在登录卡片标红。凭证统一存本地键值库，区分凭证库与开关库。

### ② 活动列表（分页参数位置是高频根因）
列表入口按平台分发。高频陷阱：分页参数放在 query string 还是 JSON body，服务端可能只认其中一种；参数位置错了会表现为「永远只取第一批旧记录」，需用直连对照四连法定性（服务端静默忽略参数 ≠ 服务端数据陈旧）。空响应、错误文案与成功谓词逐平台记录。

### ③ 下载链路（按源特化）
下载入口按来源分发到各平台客户端；不同来源返回的文件种类（FIT/GPX）与后续修补不同。下载有效性判据：FIT 长度足够且魔数正确；过短判无效；他人记录 403 按无权限跳过，不计同步失败。下载后按来源做归一化、坐标纠偏等修补。

### ④ 上传引擎分发
上传入口先做预处理（格式是否需要预转、GPX 时间是否需要修正），再按目标平台分发到各上传分支；返回结果模型区分成功、跳过（判重）、待入库（异步入库）。待入库分支不计为已落库，需等待入库时间后到目标平台核对。

### ⑤ 时区 / FIT / 坐标处理链
- 下载端：按来源做时间归一化（依据文件内时间字段是否存在判定基准），坐标按来源坐标系纠偏（火星坐标回 WGS-84；下载端已转过的不要二次纠偏）。
- 上传端：GPX 按目标时区修正时间；FIT 按当天 / 历史活动分治平移。两套平移逻辑不能同时跑，防止叠加成 ±16h；验证要看目标平台网页端开始时间。

### ⑥ 本地缓存库
缓存库通常承担三类用途：活动缓存（去重、增量、文件名映射）、同步统计（成功 / 跳过 / 失败 / 上次同步，作为登录卡片徽标源）、平台操作日志。公开梳理只保留用途描述，不展开表结构与索引细节。

### ⑦ 后台任务 / 前台服务
后台任务在无界面环境下调度同步；前台服务持有通知与渠道；各来源条间有节流间隔，下载并发可配置，风控敏感平台强制串行。

## 三、陌生代码库的锚点定位方法

1. **先找入口分发**：从同步入口、登录入口、下载入口的分发逻辑入手，确认平台枚举与分支条件，再沿各平台客户端下钻。
2. **检索关键词定位**：接口路径片段、请求字段名、错误文案、缓存键名、文件魔数、时间字段名，都是比类名更稳的检索入口。
3. **区分两类陈旧**：「参数被静默忽略导致永远旧数据」与「服务端本身数据陈旧」要分别对照直连请求定性，避免误判。
4. **超大类只做方法索引**：体量极大的界面类 / 任务类，只标注方法索引与职责，不逐行断言；方法体未读的部分明确标未核实，不补造结论。
5. **两套基线对照**：仓库代码与发布产物不一致时，逐段对照差异，定位是发版改包还是源码回归；结论落到行为矩阵，再反查差异点。

## 四、死代码复核方法

- 对全树检索某组件的外部引用，剔除组件自身文件与其内部类文件后统计外部引用数；引用为 0 且无反射 / 多类加载槽位调用迹象，才可判为死代码。
- 不同来源的代码基线结论不一致时（例如一处记有若干引用、另一处为 0），标注两套基线不一致、未核实，改动前先确认是否被反射调用或位于其他类加载槽位。
- 确认死代码按项目保留规则处理，不在公开文档列出具体旧组件名。

## 五、版本回归定位方法

1. 先列版本矩阵：哪些版本可用、哪些版本起出现回归。
2. 二分定位到引入回归的版本，再用行为对照复现现象。
3. 先跑跨方向行为矩阵（各来源 × 各目标 × 下载 / 上传），再反查代码差异；不要先入为主改代码。
4. 回归清单覆盖：当天活动、历史活动、同条重传幂等、时区样本、异步入库样本。

## 六、分析红线

- 本仓库不发布任何反编译源码树、补丁树或安装包；不保留可还原反编译包程度的类清单、包描述符、文件计数、精确行号与数据库表结构细节。
- 保留在公开知识库中的内容限于：公开接口口径、通用格式规范、跨平台接入备忘、时区与坐标判据、现象—根因—防范类坑位方法论。
- 标「待真机验证 / 未核实」的条目均未在本环境登录平台验证，对接前需真机回归。
