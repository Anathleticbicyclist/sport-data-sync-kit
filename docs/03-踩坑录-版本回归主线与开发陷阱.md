# 专题一：版本升级导致旧功能回归损坏（最高频坑型）

> 用户原话：「最多的就是升级版本、新功能好用旧功能坏掉了」。本专题是本知识库踩坑录的主线：先讲实测脉络，再讲二分定位方法、最终根因、可迁移的通用回归模式，最后给改完必跑的跨方向回归清单。

## 1.1 本知识库实测脉络

### 1.1.1 版本可用性矩阵（同设备、同账号、同 rideId 对照）

取证条件：同一台模拟器、同一 iGP 账号、同一批活动；服务端 `getDownloadUrl` 与 OSS 直链在回归版本失败期间一直可取，排除「服务端不给文件」。

| 包 | 版本对照 | 「测试」按钮结果 | 日志特征 |
|---|---|---|---|
| 基线版本 | — | ✅ 20/20 全成功 | 平台对接模块日志：`FIT downloaded: … bytes` → `✅ 上传成功: 迈金上传成功(OTM API)` → `📊 同步完成: 成功20 / 跳过0 / 失败0` |
| 相邻版本 | — | ✅ 成功（样本文件） | `FIT downloaded: … bytes (rideId=…)` |
| 相邻版本 | — | **本机未单列实测，未核实/待真机验证** | 本机矩阵只覆盖基线版本与回归版本；其余相邻版本的逐版本行为未在本机复现 |
| 回归版本 | — | ❌ 1ms 失败 | `⬇️ 下载: … (0.0km)` → `❌ 下载失败: 数据无效`，**无任何平台对接模块日志** |
| 回归版本 + 一行补丁 | — | ✅ 成功（样本文件） | `FIT downloaded: … bytes (rideId=…)` → `✅ 测试下载成功!` |

### 1.1.2 脉络要点

- 基线版本的成功不是「旧版本兼容」：同一台机器、同一 token、同一 rideId 对照。
- 服务端侧一直正常：`getDownloadUrl` 换 URL 与 OSS 直链在失败期间 HTTP 200 可取到 FIT 实体；失败发生在客户端、且是 2ms 内不发起任何网络请求。
- 早期错误归因（「iGP 端不再提供原始文件，建议改文案」）**已被实测推翻**，不要按那条改；根因与修法以实测结论为准。
- 版本增量背景：相邻版本区间的改动集中在平台对接模块、上传路由模块与 FIT 处理逻辑。

## 1.2 二分定位方法（相邻版本回归怎么查）

| # | 方法要点 | 说明 / 踩坑 |
|---|---|---|
| 1 | **先端到端跑相邻版本，拿行为矩阵，再带结论反查 diff** | 顺序不能反：先跑正常版与故障版（同设备同账号）比较日志，再去翻代码；反过来容易得出「代码等价所以与客户端无关」的错误归因。 |
| 2 | 解码基线归一化 diff：剥 label 名、去 label 行、sha256 比对 | 只比主类会漏；**协程/回调内部类必须纳入比对**，真正的网络逻辑常在这些内部类里。 |
| 3 | label-only diff 只能证明「该段代码没改」，不能证明服务端行为没变 | 若 diff 全是 label 改名，说明逻辑等价，可把该链路排除出回归嫌疑；要定因还得抓真实响应。 |
| 4 | 中文日志文案转 `\uXXXX` 反查抛出点 | 字节码里汉字全部以 `\uXXXX` 转义存储，直接 `grep "文件数据无效"` 一定 0 命中；把文案逐字转义后全树搜文件+行号，并确认旧版是否同一行号同一文案。 |
| 5 | **API 类零日志 = 入口没命中，不是逻辑算错** | 故障版整个 API 类无日志（平台对接模块从头到尾无 `FIT downloaded` 输出），等于方法根本没被调用；据此判断是分发入口没命中，而不是下载/解析逻辑算错。 |
| 6 | 沿文案附近找前置诊断日志，区分「没拿到数据」与「拿到了但内容不对」 | 如「下载 N bytes」「无下载URL」「HTTP xxx」；再决定取证方向。 |
| 7 | 相邻版本行号常常完全相同（只因 label 重命名），按行号或文件大小判断「没改」会误判，必须实际 diff。 | — |
| 8 | 不要用文件名/字段名反推「命名污染」 | 跨平台上传会保留原文件名，`kp_xxx` 可能只是历史来源标记；先向用户确认事实再定假设。 |

## 1.3 最终根因（本知识库已闭环）

### 1.3.1 一句话结论

**回归版本发布包里，主界面模块的下载活动方法被手改坏了一个分发常量：分发常量由开改关。** 这个比较值不是死变量，它是 `when(source)` 分发链的第一个比较值。

### 1.3.2 因果链

| 环节 | 事实 |
|---|---|
| 分发表 | `IGPSPORT` case 号 = **1**；`IGPSPORT_INT`=2、`XINGZHE`=3、`MAGENE`=4、`GIANT`=6… |
| 被改坏的常量 | 基线版本 = 1，回归版本 = 0 |
| 第一次比较 | 分发链第一个比较值，与枚举映射结果比对 |
| 凭证判空 | `getCredential(source)` 为 null 才 `return null`（iGP token 在，这条不成立） |
| iGP 分支 | 取 `id` / `extra`，调平台对接模块 `downloadFitFile(...)` |
| 失败判点 | 返回 null / 文件小于 100 字节 |
| 失败文案 | 「❌ 下载失败: 数据无效」/「❌ 文件数据无效」 |

回归版本里 `1 != 0`，iGPSPORT 不进下载分支，顺着 2/3/4/… 一路比不中，落到 default **直接 `return null`**；调用方拿到 null → 打印「❌ 文件数据无效」。平台对接模块本身一行没改（基线版本 vs 回归版本逐字节等价），所以日志全程没有 `FIT downloaded` 输出。

### 1.3.3 关键认知（容易误判的四点）

1. **常量被编译器 hoist 到方法序言，不是死变量**：Kotlin 编译器会把 `when` 的 case 号常量 hoist 到方法序言；「序言里的常量」完全可能是控制流常量。
2. **巨型方法里同一槽位会被复用**：不能因为「某变量后续被重新赋值」就判定某条常量赋值是死代码。
3. **发布产物与仓库代码基线不一致时，先核对哪份是实际出包读取的事实源**：仓库代码基线本来就是正确值；回归来自「发版时的本地改包」，不是仓库代码。
4. **修复 = 改回常量一行，无副作用**；应急热修包只是「在坏包上贴膏药」，与仓库源码不符，下次发版可能再被覆盖回 0。

### 1.3.4 修复与发版注意

- 方案 A（推荐）：以仓库代码基线为基线（本来就是正确值，无需改），版本号提到下一发布版本，全量重编后真机实测通过再 push / 发 Release。
- 方案 B（应急热修）：在坏包上一行改回 + 全量重编 + 对齐 + 签名，可覆盖安装、登录态不丢；**只建议验证用，不作为正式发版**。
- ⚠️ 重编前必须删掉 `build/` 缓存（缓存会静默复用旧字节码，见专题二 T8）。

## 1.4 通用回归模式（可迁移到其它逆向项目）

| # | 通用模式 | 本知识库实例 | 迁移时怎么查 |
|---|---|---|---|
| 1 | **被 hoist 到方法序言/方法外的常量、枚举映射，在加功能时被误改** | 序言常量由 1 改 0，iGP 分发落空 | 回归 diff 里先看序言常量与比较值；不要把序言常量当死变量。 |
| 2 | **Kotlin `when` 的 case 号与 `$WhenMappings` 对应关系被打乱** | IGPSPORT case=1 | 先读枚举映射拿每个 case 号，再找调用处核对是否相等；不等就顺链落空走 default。 |
| 3 | **build 缓存静默复用旧字节码，导致「改了没生效」的误判** | 每次改动必须先删 `build/` 全量重编 | 见专题二 T8。 |
| 4 | **新功能接入改了共享入口（合成方法、Api 基类、统一上传路由），波及旧方向** | 全项目只有上传路由内部入口一处收口上传 iGP；改它要覆盖所有发 iGP 的路径 | 回归前先画共享入口调用图：谁调这个合成方法/基类/路由，旧方向有没有共用。 |
| 5 | **归一化 diff 把唯一实质差异当「版本号/常量噪音」忽略** | 归一化后只报 1 处差异，被当成版本号/常量写法噪音；实际它是唯一实质差异 | 单文件只报 1 处差异时不要直接判等价；逐处看常量值与比较。 |
| 6 | **项目自述 release notes / README 不能当根因证据** | README 旧版本更新日志写「修复迈金 token 过期后不自动刷新需重新登录」，但实测刷新链仍不完整；实测可能与说明无关 | 根因只认「直连响应 + 客户端实拍批次」两条证据同时成立；release notes 仅作线索。 |
| 7 | **两套代码基线并不同步，改错基线会出现「改了但没生效」** | 仓库快照（滞后）与官方解码基线在版本号、佳明分支等至少四处实质不同 | 见专题二 T12。 |
| 8 | **从坏包/基准基线重新派生补丁，等于在坏包上贴膏药** | 应急热修包与仓库源码不符，下次发版可能被再次覆盖回 0 | 新基线必须从「已通过的补丁基线」派生，先 diff 上游基线与基准基线确认补丁清单。 |

# 专题二：其它已记录陷阱

> 每条严格五段式：**现象 — 根因 — 当时怎么定位 — 怎么修 — 复发防范**，末尾标注置信度。T1–T23 为已记录陷阱。

## T1 分页参数 body/query 契约错位（服务端静默忽略，恒返回第 1 页）

- **现象**：App 单条下载正常，但同步/批量列表永远只取同一批旧记录；「跳过 N 条」无效；同步数量填大仍只处理默认条数（20 条）。模拟器实拍：20 条全是 10-11~10-13 旧记录，iGP 第 1 页最新的 5 条（11-05~11-11）根本没被取到。
- **根因**：
  - **迈金 OTM**：平台对接模块把 `page`/`limit` 作为 JSON 字段塞进 body；实测 body 里的 page 被服务端静默忽略，`current_page` 恒为 1，三次返回同一批最新 20 条；query string `?page=2&limit=20`（body 空 `{}`）才生效，`current_page=2`。
  - **iGPSPORT**：平台对接模块拼 `?pageNo=`，上层把「跳过」条数直接当 pageNo，没有 `skip/size+1` 换算；跳过=0 → `pageNo=0` → 服务端 `code=1003` 空响应；跳过=20 但总共只有 8 页 → 空/异常；只有跳过正好落在 1..8 才有数据，且拿到的是那一页，不是「最新 20 条」。
- **当时怎么定位**：用应用真实 token 绕过 App 直连列表接口做三点/四点对照——`page=0` / `page=1` / 末页 / query 版 `page=2`，只读响应里的 `current_page`、`total_pages`、首条时间戳与条数；body 版与 query 版各打一次比较回显页码。服务端排序「最新在前」、两端都能正常翻页，排除服务端数据陈旧，问题落在客户端组装请求方式。
- **怎么修**（方案均为小改，未实施）：
  - iGP：`pageNo = max(1, page)`，更彻底是 `pageNo = (skip / size) + 1` 并保证 `>=1`。
  - 迈金：把 `page`/`limit` 从 body 挪到 query string，body 留空 JSON 或去掉；按同样规则做 `pageNo=(skip/size)+1, >=1`。
  - 建议补翻页补足：循环取页直到凑满 `count` 或 `has_more=false`；失败可见化：把 HTTP 码、pageNo、pageSize 打进日志。
- **复发防范**：
  - 服务端对错误参数常「静默忽略」：body 放 page 仍返回 HTTP 200 和完整一页，只是永远第 1 页，不报错，容易误判成服务端数据陈旧。
  - 页码 0 不是所有接口都等价第 1 页；有的直接返回业务错误码 + 空列表（iGP `code=1003`）。
  - 只看首条是否最新不足以判断分页，**必须同时验证第 2 页与第 1 页不重叠**。
  - GET 与 POST 可能不同：同一路径 GET 报 405 时不要就此判定接口不可用，按客户端实际方法（POST + JSON body）复现。
- **置信度**：迈金「服务端只认 query」代码侧仅能证实「App 把参数放 body」，服务端行为结论来自既有实测文档 + 模拟器旁证，**未在本机重放，待真机/抓包复核**；iGP `pageNo=0` 业务错误码为直连实测。

## T2 时区标记不生效、双轨叠加 ±16h、字段形态混用与锚点法

- **现象**：同步到 iGPSPORT / 迈金等平台的活动，网页端开始时间偏早或偏晚整 8 小时，极端样本偏 16 小时；当天与历史活动表现不一致。设置页时区开关已开（设备实测历史/当天标记均为 1），但上传路由模块的整段日志里一条「iGP时区修正+8h（按平台设置）」都没有。
- **根因**（四条互相独立，叠加出现）：
  1. **标记开着 ≠ 分支命中**：标记=1、方法在上传路由内部入口里被无条件调用，但 iGP 时区平移方法的判定没命中，返回原字节；靠「再补一个标记判断」解决不了，需要不依赖标记的自判逻辑。
  2. **目标文件缺 `local_timestamp` 字段，导致「两字段相等」条件永不成立**：行者 normalizer 的触发条件是 `local_timestamp - timestamp == 0`，前提是两个字段都在；迈金文件里根本不存在 local_timestamp 那一档本地时间值，照搬行者规则会判定「不需要修正」→ 原样返回 → bug 依旧。
  3. **两套平移逻辑叠加成 +16h / −16h**：下载端归一化（FIT 处理逻辑）、上传端 GPX 本地时间目标回写、iGP 专用时区平移方法三套偏移并存且互相不知道对方；行者 FIT 下载端已加过 8h、上传开关又选 +8 → 叠加 +16h；行者 GPX → iGP 开关选 −8 档，减 8h 后平移方法再减 8h → −16h（路径已证实成立）。
  4. **当天/历史键名对调**：时区平移方法当天活动读了历史键、历史活动读了当天键；即使偏移量正确，用户配的桶也用错了对象。
  5. **人工勾选 prefs 布尔不可靠**：标记为 1、方法也被无条件调用，日志却一条修正都没有；自判要按文件内容看，不能按设置页勾选看。
- **当时怎么定位**：
  - 用真实导出的 FIT 做定向字节检索（FIT 时间戳 = 距 1989-12-31T00:00:00Z 的秒数；FIT 头长度取 `header[0] & 0x0F`，不是 `>>4`）：分别算「UTC 正确」与「本地钟面当 UTC」两组 4 字节值，大端/小端都试，命中哪组即文件时间基准；再确认 activity(mesg 34) 是否带 local_timestamp(field 5)。
  - 实测迈金那份样本文件：UTC 正确值命中（大端），本地钟面值未命中 → 纯 UTC 文件、无本地字段；iGP 服务器按 UTC+8 直读该数值，显示成偏早 8 小时的钟面时间而不是采集时间。
  - 组合矩阵逐格推演：源类型 × 目标 × 文件时间 × 开关档位 × 代码实际偏移，标出 +16h / −16h / ±8h 风险格。
- **怎么修**：
  - **锚点法（推荐的统一判据）**：不看文件形态，直接和「这条记录真实的开始时间」对齐。锚点取上游列表已解析的本地状态层 `startTimeMs`（解析自 `start_riding_time`，是 UTC 正确的 epoch 毫秒）。公式：`target = startTimeMs/1000 + 28800`；`shift = target − 文件内 timestamp(253) 秒值`。三种形态自动归一：纯 UTC → +8h；本地冒充 UTC（两字段相等）→ 0；规范分离（差 28800）→ +8h；解析不出 activity → 不动兜底。
  - **三条护栏（必须写进实现）**：① 幂等：平移后 `ts == target`，重传 `shift==0`，不叠成 +16h；② 量程：`|shift| > 12h`、或 shift 不是 3600 整数倍 → 判定锚点/解析异常，不动并打日志（宁可不改，不能改错）；③ 锚缺失：`startTimeMs <= 0` → 退回字段法兜底（无 local → +8h；`local==ts` → +8h；否则不动）。
  - 配套小修：交换两行键名；堵住行者 GPX→iGP 的 −16h 重复减 8；行者桶默认不调整。落点仍在上传路由内部入口；FIT 处理逻辑查找 activity 的方法由 `private` 改 `public` 一个词即可复用，字节数组平移方法已是 public static。
- **复发防范**：
  - 两个平移逻辑不能同时跑：原平台「按标记 +8h」开关若还开着，叠加自判会变 +16h；改造用「来源分流」而不是「追加一次调用」。
  - 下载端已归一化的文件，上传端手动开关保持「不调整」；验证要看目标平台网页端活动开始时间，不要只看接口返回或本地缓存。
  - 按「有没有某字段」分支也不行：混用形态下「缺字段」与「字段相等」各自对应不同处理，条件互相打架；同一来源会混着出三种形态。
- **置信度**：键名对调、−16h 路径已证实；各平台网页端最终取 UTC timestamp 还是 local_timestamp、normalize 两字段精确语义，需真机样本升级为已证实。

## T3 token 刷新与回写（迈金被动刷新一次、refreshToken 不回写、401/403 判定）

- **现象**：迈金（顽鹿 OTM）每当有新活动需要拉取时，本地登录态/令牌不可用，必须先打开顽鹿 OTM 重新登录一次，本次同步才能成功；无新数据时列表返回空、看起来正常。
- **根因**（置信度梯队）：
  - **R1（已证实，代码层事实）**：刷新策略被动且不完整——除启动检测一处 `<1h` 预检外，列表/下载/上传前均无主动刷新；401 后仅按异常文案子串匹配（`"过期"` / `"401"`，不含 `"403"`、不按 code 判定）刷新一次；刷新只回写 access_token，**从不解析/回写服务端可能轮换的新 refreshToken**。
  - **R2（高可能，待实测）**：服务端每次刷新轮换 refreshToken（一次性刷新令牌），本地漏存新值，第二次刷新用旧 refreshToken 被拒，`refreshToken` 因 `data.token` 为空静默返回 null，调用方不再重试，最终提示重登。
  - **R3（待实测）**：服务端在新活动入库后使旧 access token / 会话失效（本地代码无法证实）。
  - 401 处理现状：客户端网络层只设超时与 `followRedirects`，**未注册任何 Interceptor / Authenticator**，不存在 HTTP 层自动 401 重放；接口层命中 401（HTTP 401 或 body code 401）直接抛 `Exception("迈金登录已过期，请重新登录")`，自己不刷新不重放；上传链路连被动刷新都没有。
  - **相邻版本把 403 也并入重登分支**（基线版本只判 401）：这不是根因，但会让「403 但非鉴权」的情况也被说成「请重新登录」，把排查方向带偏。
  - **Wahoo 对照**：Wahoo 401 时刷 token 重试一次（主界面模块内捕获），与迈金不同构。
- **当时怎么定位**：
  - 全仓扫描刷新令牌写回点：仅 WebView 初次登录与启动检测两处，且启动检测写回的是刷新前取出的**旧**值；三处刷新调用点都只回写旧令牌。
  - 解码 JWT payload 实测 TTL：access 约 48 小时、refresh 约 58 天；「每条新数据都要重登」不可能由 TTL 造成。
  - 模拟器 root 改凭证库 xml 构造四场景（原样 / access 失效 refresh 有效 / 关自动检测 / 双失效），证实 401/403 后客户端确实会主动刷新并重试，刷新成功就继续同步，只有刷新本身失败才落「请重新登录」。
  - 基线差分：基线版本 → 回归版本迈金鉴权链路零逻辑改动（逐文件比对），该缺陷从初版就有，**不是相邻版本回归**。
- **怎么修**（方案 1 最小改动，未实施）：
  - 治本项是 R2 回写：平台对接模块加实例刷新令牌字段 + getter；解析 `data.optString("refreshToken","")`，非空写入实例字段；三个返回通道刷新成功后读 getter 落凭证库，新值空则保留旧值不覆盖。
  - 拉列表前按令牌剩余时长做与启动检测同构的 `<1h` 预检。
  - 配套：把刷新接口的 HTTP 状态码与响应体 message 一起打进日志，区分「refresh 被拒（需重登）」与「网络错误（可重试）」。
  - 方案 2（后续加固）：OkHttp Authenticator 统一 401 重放，属新类，走独立类流程。
- **复发防范**：
  - 刷新响应里若带回新 refreshToken 必须回写；服务端不轮换时回写是空操作，无副作用。
  - 预检阈值与现有启动检测的 1h 保持一致，避免「启动刷过、进同步又刷一次」双刷新；重复刷新若触发服务端轮换，反而是 R2 的放大因素。
  - 后台任务 / 前台任务两条链路不走 `fetchActivities`，覆盖不到；前台任务全文件无 refreshToken 读取/写回，连被动重试都没有，要自愈须单独补落点。
  - 待真机抓 `/api/token` 响应确认是否轮换：响应带新 `refreshToken` 而 Prefs 未变 → 回写未闭环。
- **置信度**：R1 已证实；R2/R3 待真机抓包验证。

## T4 prefs 路径 / uid 写错导致账号态被清空

- **现象**：root 直接改设备上的 SharedPreferences 文件构造测试场景后，整个账号态被清空、解析失败；或凭证读不到、登录态全丢。
- **根因**：
  - **prefs 文件名/键写错**：凭证库是凭证库 xml（token / 运行日志），平台时区开关库是开关库 xml；凭证键按 uid 维度存取。文件名或键名写错会读到空库。
  - **文件属主 uid 写错**：root 改 prefs 文件前必须先停止应用进程；文件属主必须是应用真实 uid（以实测为准），写成别的 uid 会让 SharedPreferences 解析失败、整个账号态被清空。
- **当时怎么定位**：四场景实验前先停止应用进程、核对文件属主与属组；对照两份 prefs 文件（凭证库 xml / 开关库 xml）的键表（本地状态层一表可查）。
- **怎么修**：改回正确文件名、凭证键与 uid 属主；覆盖安装（同签名）保留应用数据与 WebView cookie，只有卸载或清数据才会丢。
- **复发防范**：
  - 直接改设备 prefs 文件的操作 SOP：停止应用进程 → 改内容 → 属主保持应用真实 uid → 再启动；改前备份原文件。
  - 新增凭证键先在本地状态层键表登记，区分凭证库与开关库；登录态判定方法只判凭证键非空白，不看 refreshToken 是否存在、也不看 exp，判定逻辑别照搬。
- **置信度**：已证实（本机模拟器实测）；具体 uid 随设备/安装变化，以实测查看包属主信息为准。

## T6 巨型方法内插代码易触发运行时校验失败；新逻辑抽成独立方法或独立类

- **现象**：往巨型方法中间插代码、内联新类/多段代码后，汇编通过，但装机启动/进页面即闪退，运行时校验失败；或类型流冲突、整个类被拒绝加载。
- **根因**：
  - 运行时在类加载/方法执行时做类型流校验；巨型方法中间插入代码会改变类型流，触发校验失败。
  - **汇编通过 ≠ 运行时校验通过**，校验失败只有真机/模拟器启动才暴露。
- **当时怎么定位**：运行日志全局过滤运行时校验失败 / 应用崩溃 / 类未找到；对照插入点前后类型与存活区间。
- **怎么修**：
  - 新逻辑封装成独立静态方法，在合成小方法里调用；新增 UI 代码追加到方法末尾，或放进独立类。
  - 新增独立类走独立类流程；主工程巨型方法内只留一次调用，入参用基本类型/已有模型类，新类不访问宿主类私有字段。
  - 改动分界线：只改常量（版本号/间隔/阈值）、单条调用替换可留在巨型方法内；需要新数据结构、多段局部逻辑、多辅助方法或两处以上复用的，必须抽类走独立类流程。
- **复发防范**：
  - 改完必须冷启动冒烟（链路 ④），不能只看汇编 exit=0。
  - 抽离段若引用宿主类私有字段/Prefs 实例，改为参数传入；抽离前后类型逐条对齐。
  - 新类不回指宿主类；新增后确认回编纳入新类、装机后类可被加载。
- **置信度**：已证实。

- **现象**：手改二进制资源清单文案后装机，关于页/设置页 inflate 即闪退，系统原生解析器判二进制资源损坏。

## T8 build 缓存静默复用旧字节码（「改了没生效」误判）

## T9 kp_ 他人记录 403「不能下载他人运动记录」（独立问题，非客户端回归）

## T10 UploadResult pending 导致「显示成功但平台没数据」

- **现象**：批量/任务/后台同步跑完，报告里某条记为成功（✅ 或 🕐 待确认），但登录目标平台网页端查不到对应活动；下次同步本端直接跳过，不再重传。
- **根因**：异步平台「已提交、后台入库」状态在引擎侧被压成 `success=true / pending=false`；调用方拿到 success 就立即写同步记忆（`addSyncedId`），一旦平台侧异步失败，本端永久跳过不再重传。`UploadResult` 五参结构（success/targetId/message/skipped/pending），全仓构造点扫描后**只有 Outbase** 按文案含「待处理」显式置 pending=true；iGP 异步解析分支（data 空/null）与迈金（HTTP 200 + `success_count>=1`）语义上是后台异步，却都被编码成 `success=true / pending=false`。pending 分支本身不写记忆键（三处读取点一致，已证实），但仍把单条计入成功合计。
- **当时怎么定位**：扫描全部 `UploadResult` 构造点、回溯 mask 与 pending 实参；`getPending()` 全仓仅 3 个读取点（批量、任务、后台），三处 pending 分支内均无 `addSyncedId`。
- **怎么修**（方案 1 最小改动，未实施）：iGP 异步分支构造时补打 pending=1；迈金/Outbase 成功路径与接口方确认是否异步入库，仅回 ACK 的结果同样打 pending；三处 pending 计数从成功合计拆出，单列「待确认」桶，文案保持 `已上传待确认`，不与 ✅ 成功混用。方案 2 为 `PendingConfirmManager` 二次确认队列（新类，走独立类流程），延迟 15–30 分钟回查列表/详情，命中再补写记忆键，指数退避重试 N 次。
- **复发防范**：
  - 异步入库平台（迈金上传后约 15–20s 入库、iGP 异步解析）**等一下再查平台**；上传判定别只用「data 非空」或「HTTP 200」。
  - 改打 pending 后回归当天/历史样本、迈金 `success_count` 为 0 两种回包、Outbase「已存在(跳过)」分支；三处计数口径（批量报告/任务报告/Worker 通知）一起核对。
- **置信度**：构造点/读取点/记忆键写入位置已证实；平台侧异步失败后未落库的后果表现待实测账号验证。

## T11 死代码误改无效（几代时间修正器只有一套被引用）

- **现象**：怀疑某工具类是改方案后留下的死代码；改了它发现行为完全没变化，难以察觉。
- **根因**：仓库里留着多套同类工具类（几代时间修正器），只有一套被外部引用。全树扫描后，旧几套外部引用 **0 命中**，第二轮裸名兜底扫描与反射形式 `Class.forName` 也未发现；现行生效的是当前 FIT 处理逻辑。
- **当时怎么定位**：按类型描述符统计，剔除类自身文件与内部类文件后看外部引用是否为 0。
- **怎么修**：死代码**保留不动**，在说明文件登记为「待确认后清理」；误改它们不会影响线上行为，也别投入排错时间。将来清理前必须重跑全树检索复核。
- **复发防范**：
  - 接手先判定生效源（见 T12），再顺调用链从 UI 入口/主循环走到目标方法，确认分支被枚举 switch 覆盖。
  - 不要凭印象复活已删除/已回退逻辑：复活旧一刀切时间修正器会与现行归一化方案叠加成 ±16h。
- **置信度**：已证实（全树扫描）。

## T12 改错基线：两套代码基线不同步 + Kotlin 镜像过期

- **现象**：照仓库 Kotlin 源码改，会把后加功能改丢；照补丁基线改却拿官方基线回编，出现「改了但没生效」的假象，版本号一路错下去。
- **根因**：
  - 项目是「官方 APK 反编译 + 补丁」流水线，不是 Gradle 源码出包；仓库 Kotlin 镜像停在旧版本，缺 CyCity、本地文件夹、iGP 国际、课表同步、轨迹合并、贴纸、热力图、码表等后加功能，只作语义参考。
  - 仓库快照与官方解码基线至少四处实质不同：版本号、APP_VERSION、佳明分支、UA。
- **当时怎么定位**：功能差集验证——在 Kotlin 镜像里搜新增平台枚举/引擎类/工具方法，缺失即说明镜像落后；逐处核对两套基线版本号与关键分支。
- **怎么修**：改动一律以与手上包同源、已验证可回编的官方解码基线为准，改完再把差异回写仓库代码基线，避免二次分叉；补一份事实源说明，把「哪套基线是事实源、版本号对齐点、中文检索约定」写死；发版前机械核对 `BuildConfig` / 本地状态层 / 版本号 / 佳明那处。
- **复发防范**：
  - 同名类在多处出现（仓库代码基线与解码工作基线），先确认改的是回编流水线实际读取的那一份。
  - 两种形态语义相同文本不同；以仓库现有文本为底做最小改动，或接受整文件替换并在 commit 说明。
  - 不要从官方基准基线重新派生补丁（会丢掉已验证补丁）；先 diff 上游基线与基准基线确认补丁清单，从已通过补丁基线派生。
- **置信度**：已证实（逐处复核）。

## T13 非 ASCII 字符以转义存储，直接 grep 0 命中假象

- **现象**：在代码全树搜中文日志文案（如「文件数据无效」），逐字 grep 0 命中，误判「代码里没有这个字符串」。
- **根因**：这批字节码里所有非 ASCII 字符都以 `\uXXXX` 转义存储，源码里看不到中文。
- **当时怎么定位**：把目标文案逐字转成 `\u6587\u4ef6...` 拼接再搜索；或按行解码后匹配（行号与原文件一致）。
- **怎么修**：检索前先确认工具可用；定位抛出点后沿文案附近找前置诊断日志。
- **复发防范**：交接/说明文档里写死中文检索约定；不要凭 grep 0 命中就下「无此逻辑」结论。
- **置信度**：已证实。

## T14 版本号多处手工维护，本地状态层不读 BuildConfig

- **现象**：关于页显示回归版本号，但启动 banner / 更新检查弹窗 / 热力图 UA 仍自称旧版本号；更新检查永远误报「有新版本」，或反之永远不提示。
- **根因**：版本号散在多处手工维护，且本地状态层不回读 `BuildConfig.VERSION_NAME`（两套基线 `BuildConfig` 引用计数均为 0），改 BuildConfig / 关于页不会自动校正更新检查基线。
- **当时怎么定位**：逐处核实现值（打包配置、分发比较基线、更新文案、关于页、UA）；硬编码基线低于线上最新 Release 时，比较结果恒为「检测到新版本」。
- **怎么修**：方案 1 当次发版逐处对齐；方案 2（根治）让本地状态层改读 `BuildConfig.VERSION_NAME`，去掉硬编码，版本号只在一处维护。
- **复发防范**：发版前按对齐点清单逐项核对，漏一处仍会误报；核对 Release 版本号格式（纯版本号与带 v 前缀）在 `compareVersions` 分段比较下仍正确。
- **置信度**：已证实。

## T15 文档自述 / release notes 与代码相反，以代码为准

- **现象**：导览/README/修改说明里写的分支方向与实际代码相反，照着文档改会把人带反方向。
- **根因（已记录的两处冲突）**：
  - FIT 处理逻辑方向：导览称「偏移=0 则 +28800、偏移=+8h 则原样」；代码实际是 `delta==0 → 原样`、`delta≠0 → shift(+28800)`。**以代码为准**。
  - README 旧版本更新日志写「修复迈金 token 过期后不自动刷新需重新登录问题」，但实测刷新链仍不完整（不回写 refreshToken、上传链路无刷新）；release notes 不能当根因证据。
- **当时怎么定位**：读代码分支逐条核对；文档与代码冲突处在正文标注。
- **怎么修**：以代码行为为准修正文档；冲突未澄清前不按文档结论动手。
- **复发防范**：定位结论必须能回落到 `文件:方法:行号`；置信度三档（已证实 / 高可能 / 待实测）分开标；文档自述仅作线索。
- **置信度**：方向冲突已证实；normalize 两字段精确语义待真机样本确认。

## T16 403 分支维护基线缺失，从补丁基线重编会丢 403 识别

- **现象**：若从维护基线重编下一版本，服务端返 403 时不再识别为登录失效、不触发重试，退回基线版本的「迈金列表错误」文案。
- **根因**：三套基线对比平台对接模块——基线版本只有 401；官方基线有 401 + 403，HTTP 层与 body code 层各两条判定；维护基线比官方基线少 4 条判定，无 403 分支。且被动重试匹配串只含 `"过期"` / `"401"`，不含 `"403"`、不按 code 判定。
- **当时怎么定位**：三套基线逐行 diff；403 在维护基线落「迈金列表错误: 」文案，不含「过期」/「401」→ 重试不触发。
- **怎么修**：随方案 0 同批回填 403 判定（HTTP 层与 body code 层各补比较分支），目标分支均为既有分支，不新增标签；不建议把调用方匹配串扩成 `"403"`（维护基线 403 落列表错误文案，匹配不到状态码）。
- **复发防范**：重编前核对维护基线与官方基线的分支完整性；403 回填后「迈金列表错误」仍承接其他业务码，勿把 403 误并入该分支。
- **置信度**：已证实（三套基线逐行对比）。

## T17 写回值时字符串与长度/类型不要共用同一槽位；空值不要覆盖旧值

- **现象**：照草稿写回写逻辑后，新 refreshToken 永远存不进去，看起来改了其实没改。
- **根因**：若取到字符串后又计算长度并覆盖同一槽位，存进去的是默认空串；长度把字符串槽位覆盖成 int，等于字段永远空。合成访问器里的入参槽位不能当临时用。
- **当时怎么定位**：逐槽位核对存活区间；选外层对象死后不再使用、目标槽位全方法 0 引用的位置。
- **怎么修**：字符串槽位与长度槽位必须分开，存字段用字符串那个；新值非空才写字段，空则保留上一次值；临时值只用死亡槽位，不占入参槽位。
- **复发防范**：
  - 扩槽位前全方法扫描无硬编码高编号槽位；入参槽位为符号别名，汇编器按槽位数自动重映射。
  - suspend 方法内联刷新必须按既有状态机模式：溢出变量落 lambda 字段 → 写 label → 调 suspend → 结果等于 SUSPENDED 哨兵则 return → resume 块还原变量续跑；不补 resume 分支接不回去。
  - 不得在分发表中间插指令；新分支必须同时进对应分发口。
- **置信度**：已证实（槽位引用计数实测）。

## T18 监听器方法名 / 跨类 private 调用签名坑

- **现象**：点体验弹窗确认按钮闪退（跨类访问受限）；或抽象方法未实现闪退。
- **根因**：
  - 界面类的 lambda 类跨类调用宿主类 **private** 静态方法 → 访问受限；修复是把该方法由 private 改 public。
  - 监听器接口方法名必须精确：点击监听接口是 `onClick(DialogInterface,int)`，写成 `onItemClick` 会抽象方法未实现闪退。
- **当时怎么定位**：全库扫描全部 lambda 类对宿主类 private 方法调用（历史仅此 1 处隐患，其余 0）；运行日志按异常类型定位。
- **怎么修**：跨类调用的宿主静态方法改 public；监听器按接口签名写方法名与参数。
- **复发防范**：新增 lambda/监听器后，冷启动 + 点一遍弹窗按钮冒烟；运行时校验失败/访问受限/抽象方法未实现/二进制资源损坏纳入链路 ④ 过滤项。
- **置信度**：已证实（历史修复记录）。

## T19 主类加载槽位方法数逼近硬上限，新类必须落备用类加载槽位

- **现象**：继续把新方法/新类堆进主类加载槽位，打包/类加载阶段出问题；新增类后主类加载槽位类型数超上限。
- **根因**：单类加载槽位 `method_ids` 有硬上限；实测主类加载槽位方法引用已逼近上限，备用类加载槽位尚有余量。
- **当时怎么定位**：解官方包各类加载槽位头 `method_ids_size` 实测；扫描各类加载槽位方法数。
- **怎么修**：新类落到独立备用类加载槽位，避开现有类加载槽位；历史上新增类曾把部分包名目录移到备用类加载槽位缓解。
- **复发防范**：不在主类加载槽位继续堆新方法；每阶段新增后确认回编纳入新类加载槽位、装机类可加载。
- **置信度**：已证实。

## T20 启动检测串行 300ms 触发风控；「10 枚上限」属 Wahoo 非佳明

- **现象**：冷启动后登录卡片逐个校验，密集请求易触发佳明 429 账号风控；排查时把 Wahoo 令牌额度错记到佳明头上。
- **根因**：
  - 启动检测对 21 个已登录平台串行发真实校验请求，条间固定 300ms；佳明对同一账号/设备/IP 短时间频繁登录（尤其失败尝试）临时限流 429 或人机验证，冷却期数小时到一天。
  - **「10 枚未撤销令牌上限」是 Wahoo**，不是佳明；佳明侧风险是 429 账号级风控，429 立即停止后续通道。
  - 佳明明文账号口令直登**仅佳明中国区**；佳明国际区全程 WebView ticket → DI token 交换，不接触账号密码。
- **当时怎么定位**：逐平台核对校验请求与间隔常量；区分两类风控的所属平台。
- **怎么修**（方案 1 最小改动）：启动检测条间 300ms 调到 2s；风控敏感平台（佳明/Outbase/迈金）只调大间隔、不整段跳过。方案 2 新增「启动检测平台开关/节流器」静态类，走独立类流程。
- **复发防范**：
  - 调大间隔后卡片标红延后，后台协程不卡 UI；被跳过平台失效态要等下次启动或实际同步才暴露。
  - 不得把 CN 明文兜底放开到 COM；不要复活已删的本地状态层；调试时别反复跑启动检测。
- **置信度**：已证实（分支判断/间隔常量/调用链实测）；风控冷却时长为服务端行为。

## T21 手写 FIT 解析器：dev 字段位误读导致位置错位

- **现象**：自写 FIT 解析器定位 activity 消息静默返回 null，或字段解析错位。
- **根因**：定义消息的开发者字段并非总存在：必须按 record header 的 bit5（0x20）判断，该位为 0 时没有 dev count 字节；误读会把后续字段位置全部错开。
- **当时怎么定位**：对照 FIT 协议 record header 标志位逐字节核对；用两组候选时间戳字节检索反推文件形态。
- **怎么修**：解析前先判 bit5 决定是否读 dev count；`findActivity` 找不到时兜底原样返回，不抛错中断主流程。
- **复发防范**：FIT 头长度取 `header[0] & 0x0F`（不是 `>>4`）；时间戳纪元 1989-12-31T00:00:00Z；解析异常 Throwable 兜底原样返回。
- **置信度**：已证实（历史踩坑记录）。

## T23 列表字段名缺口：`rideDistance` 未解析导致 0.0km（侧线独立问题）

- **现象**：记录中心活动显示 `(0.0km)`；与下载失败是两条独立问题，不影响下载字节。
- **根因**：iGP 列表返回的距离字段名是 `rideDistance`（另有 `totalMovingTime`、点分 `startTime`），而兜底链只查 `Distance` → `distance` → `sportDistance`，全仓库未读取 `rideDistance`（Grep 0 命中）；距离取空显示 0.0km。列表 `extra`、`distance_km`、`duration_sec` 全空只影响显示与文件名，不影响下载字节。
- **当时怎么定位**：真机/模拟器日志调试转储列出首活动 JSON 键名，与兜底链字段名逐一比对。
- **怎么修**：distance 兜底链追加 `rideDistance`，沿用既有 ≥1000 ÷1000 换算；真机核对单位（米/千米）避免重复换算。
- **复发防范**：默认值 -1.0 到显示 0.0 的折算位置（缓存/读取层）待真机核对；解析新平台列表字段时先 dump 原始 JSON 键名再写兜底链。
- **置信度**：字段名缺口已证实；-1.0→0.0 折算点待真机核对。
