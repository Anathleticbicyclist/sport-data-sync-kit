## 1. UTC vs 本地时间

- **timestamp（field 253）**：UTC 秒，所有平台解析的"真实时刻"基准。
- **local_timestamp（field 5）**：本地钟面秒（不带时区含义）。
- **差值含义**：`local_timestamp − timestamp = 时区偏移秒`（CST=UTC+8 时 = +28800）。
  - 差值 = 28800：规范分离（文件同时写了 UTC 和本地）。
  - 差值 = 0：文件**没做分离**——要么纯 UTC，要么"本地钟面冒充 UTC"，二者数值相同无法区分，这正是歧义根源。

## 2. 三种文件形态与归一

| 形态 | timestamp 实测 | local_timestamp | 归一动作（目标 iGP） |
|---|---|---|---|
| ① 纯 UTC（迈金常见） | 01:14:46（UTC 钟面） | 不存在 | **+28800** 让 iGP 按本地读成 09:14 |
| ② 本地冒充 UTC | 09:14:46（本地钟面） | 等于 timestamp (=0) | shift=0，**不动**（数值已是本地钟面） |
| ③ 规范分离 | 01:14:46 | 09:14:46 (差 28800) | **+28800**（与 iGP 直读 UTC+8 口径一致） |

> 教训（实测）：**靠"local_timestamp 在不在 / 相不相等"判断会漏判或误判**——同一来源（迈金）会混着出这三种形态，字段法不可靠。

## 3. 锚点法（推荐判据）

**不看文件形态，直接和"这条记录真实的开始时间"对齐。**

- 锚点来源：`本地状态层.startTimeMs`（由列表接口 `start_riding_time` 以 `Asia/Shanghai` 解析得到，是真实开始时刻的 epoch 毫秒，UTC 正确）。

```
target = startTimeMs / 1000 + 28800 # 本地钟面（CST）对应的秒值
ts = activity(mesg 34) 里 timestamp(field 253) 的秒值
shift = target − ts # 需要平移的秒数
```

三种形态自动归一：纯 UTC → +8h；本地冒充 UTC（两字段相等）→ 0；规范分离 → +8h；解析不出 activity → 不动兜底。

- 平移只动 **(mesg=34 activity, field=5 local_timestamp) 与相关 timestamp 序列**；**改完必重算 CRC**（见 `formats.md` §1.8）。

## 4. 三条护栏（必须实现）

1. **幂等**：平移后 `ts == target`；再次处理时 `shift == 0`，绝不叠加成 +16h。
2. **量程异常即不动**：`|shift| > 12h`、或 `shift` 不是 3600 的整数倍 → 判定锚点/解析异常，**原样返回并打日志**（宁可不改，不能改错）。
3. **锚缺失兜底**：`startTimeMs <= 0`（列表没给开始时间）→ 退回字段法：无 local_timestamp 或 local==timestamp → +28800；否则不动。

## 5. 字节检索诊断法

需要判断导出的 FIT 时间是否需要 ±8h 平移，或打算把 A 平台的"智能时区修正"照搬到 B 平台时：

1. 先算候选值：FIT 时间戳 = 距 1989-12-31T00:00:00Z 的秒数。分别算出"UTC 正确"与"把本地钟面当 UTC"两组值。
2. 在文件字节里定向检索这两个 4 字节值（大端、小端都试）。命中哪一组即文件的时间基准；全部不命中说明记录时间与假设不符，先用文件名/列表接口的真实时间重新算。
3. 再确认 `activity`(mesg 34) 是否带 `local_timestamp`(5) 字段：命中 UTC 值而搜不到本地钟面值，即"纯 UTC 文件、无本地字段"。
4. 平移与否按字段形态判（兜底用）：无 local_timestamp → 需要 +8h；有且与 timestamp 差值非 0 → 已规范分离，不动；找不到 activity → 不动。

注意：FIT 头长度取 `header[0] & 0x0F`（不是 `>>4`）；时间戳纪元 1989-12-31T00:00:00Z。

## 6. 平台展示口径差异（本知识库实测）

- **iGPSPORT**：把 FIT 里的 timestamp 数值**当本地钟面直接显示**。给它纯 UTC 文件（数值=01:14），它就显示 01:14，比实际骑行（09:14）**早 8 小时**。→ 上传前需把数值"加成本地钟面"（+28800）。
- **迈金（Magene）**：导出的 FIT 是**纯 UTC 正确**的（实测某样本的 UTC 秒数对应 01:14:46 UTC）。
- **行者**：文件常写"local_timestamp == timestamp"（本地冒充 UTC）形态。

## 7. 复发防范

- 两个平移逻辑不能同时跑：原平台"按标记 +8h"开关若还开着，叠加自判会变 +16h；改造用"来源分流"而不是"追加一次调用"。
- 下载端已归一化的文件，上传端手动开关保持"不调整"；验证要看目标平台网页端活动开始时间，不要只看接口返回或本地缓存。
- 按"有没有某字段"分支也不行：混用形态下"缺字段"与"字段相等"各自对应不同处理，条件互相打架；同一来源会混着出三种形态。
- 人工勾选的 prefs 布尔不可靠：标记为 1、方法也被无条件调用，日志却可能一条修正都没有；自判要按文件内容看，不能按设置页勾选看。
- 时区三套并存：下载端 `FIT 处理逻辑`、上传端 GPX 本地时间目标回写、iGP 专用 `iGP 时区平移方法`；改动任一端都要防叠加 ±16h。
- 待真机验证：各平台网页端最终取 UTC timestamp 还是 local_timestamp、normalize 两字段精确语义，需已知本地时间样本真机确认。
