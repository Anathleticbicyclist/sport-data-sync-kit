## 一、版本升级导致旧功能回归损坏（最高频坑型）

### 1. 实测脉络（本知识库已闭环案例）

- 同一台本地调试设备、同一 iGP 账号、同一批活动对照：相邻早期版本全成功；另一相邻版本成功；基线版本 1ms 失败，日志无任何对应平台客户端输出；基线版本补一行后成功。
- 服务端侧一直正常：`getDownloadUrl` 与 OSS 直链在失败期间 HTTP 200 可取到 FIT 实体；失败发生在客户端、且 2ms 内不发起任何网络请求。
- 早期错误归因（"iGP 端不再提供原始文件"）已被实测推翻，不要按那条改。

### 2. 二分定位方法（相邻版本回归怎么查）

1. **先端到端跑相邻版本拿行为矩阵，再带结论反查 diff**；顺序不能反，否则容易得出"代码等价所以与客户端无关"的错误归因。
2. 字节码基线归一化 diff：剥标签名、去标签行、sha256 比对；**协程/回调内部类必须纳入比对**，真正的网络逻辑常在内部类里。
3. 标签级 diff 只能证明"该段代码没改"，不能证明服务端行为没变；要定因还得抓真实响应。
4. 中文日志文案在字节码基线里是 `\uXXXX` 转义，直接 grep 中文 0 命中；把文案逐字转义后全树搜文件+行号。
5. **API 类零日志 = 入口没命中，不是逻辑算错**：方法根本没被调用，而不是下载/解析逻辑算错。
6. 沿文案附近找前置诊断日志（"下载 N bytes"/"无下载URL"/"HTTP xxx"），区分"没拿到数据"与"拿到了但内容不对"。
7. 相邻版本行号常常完全相同（只因标签重命名），按行号或文件大小判断"没改"会误判，必须实际 diff。
8. 不要用文件名/字段名反推"命名污染"；`kp_xxx` 可能只是历史来源标记，先确认事实再定假设。

### 3. 最终根因（已闭环案例）

- 基线发布包里 `主界面模块.downloadActivity` 被改坏一个序言常量：比较值由 1 变成 0；该寄存器槽位是 `when(source)` 分发链的第一个比较值，`1 != 0` 导致 iGPSPORT 分支落空走 default 直接返回 null。
- 四点易误判认知：
 1. 常量被编译器提前到方法序言，**不是死变量**；序言常量完全可能是控制流常量。
 2. 同一寄存器在巨型方法里会被复用，后续被重新赋值不能证明序言常量是死代码。
 3. 发布改包产物与维护基线不一致时，以维护基线为准（该例本来就是正确比较值）。
 4. 修复 = 改回比较值一行；应急热修包与仓库源码不符，下次发版可能再被覆盖回 0。

### 4. 通用回归模式（可迁移）

| # | 通用模式 | 迁移时怎么查 |
|---|---|---|
| 1 | 被提前到方法序言/方法外的常量、枚举映射，加功能时被误改 | 回归 diff 先看序言常量与比较值；别把序言常量当死变量 |
| 2 | 源码 `when` 的 case 号与枚举映射对应关系被打乱 | 先读枚举映射拿每个 case 号，再找调用处比较分支核对是否相等；不等就顺链落空走 default |
| 3 | 构建缓存静默复用旧字节码，导致"改了没生效"误判 | 改字节码基线必须先清构建目录缓存全量重编（见 T8） |
| 4 | 新功能改了共享入口（合成方法、Api 基类、统一上传路由），波及旧方向 | 回归前先画共享入口调用图：谁调这个合成方法/基类/路由，旧方向有没有共用 |
| 5 | 归一化 diff 把唯一实质差异当"版本号/常量噪音"忽略 | 单文件只报 1 处差异时不要直接判等价；逐处看常量值与比较指令 |
| 6 | 项目自述 release notes / README 不能当根因证据 | 根因只认"直连响应 + 客户端实拍批次"两条证据同时成立；release notes 仅作线索 |
| 7 | 两套代码基线并不同步，改错基线会"改了但没生效" | 见 T12 |
| 8 | 从坏包/基准基线重新派生补丁，等于在坏包上贴膏药 | 新基线必须从"已通过的维护基线"派生，先 diff 上游基线与基准基线确认补丁清单 |

## 二、跨方向回归清单（改完必跑）

> 前置：同一测试账号、同签名覆盖安装保留登录态；先扩日志缓冲、清空历史日志，再后台持续落盘；操作后按 TAG 筛关键行。

### 链路 ① iGPSPORT 导出（iGP 作为数据源下载）

- 前置：iGP 已登录；记录中心有可测活动。
- 操作：来源选 iGPSPORT，目标任选（可先选本地文件夹便于直接看落盘）；对一条本次活动点测试或开始同步。
- 看日志：`对应平台客户端` 的 `FIT downloaded: N bytes (rideId=…)`；失败关键字 `无下载URL` / `下载URL空响应` / `iGPSPORT FIT下载失败 HTTP ` / `FIT下载空响应` / `FIT文件头可能无效`；主流程 `❌ 文件数据无效` / `❌ 下载失败: `。
- 通过判据：每条都有 `FIT downloaded` 字节数；≥100 字节且魔数 `.FIT`（或合法 GPX `<?xml` 头）；不再出现"文件数据无效"。无对应平台客户端日志且 1ms 内失败 → 优先怀疑分发链常量被改坏。

### 链路 ② iGPSPORT → 迈金 上传（同时验证 iGP 下载修复未回退）

- 前置：iGP、迈金均已登录；账号活动 ≥20 条（历史基线）。
- 操作：源 iGPSPORT、目标迈金，同步一批活动。
- 看日志：`对应平台客户端` 必须出现 `FIT downloaded`；迈金上传返回 `success_count>=1`（表单字段名固定 `jilu0`）；汇总行 `📊 同步完成: 成功N / 跳过N / 失败N`。
- 通过判据：下载阶段每条都有 `FIT downloaded`；迈金侧 `success_count>=1`；失败 0（或失败项有明确原因）；迈金网页端 15–20s 后能看到记录（异步入库）。

### 链路 ③ 迈金 → iGPSPORT 上传（含时区显示正确性）

- 前置：迈金、iGP 均已登录；准备一条**当天新录**活动和一条**历史**活动；同一条可再传一次验幂等。
- 操作：源迈金、目标 iGPSPORT，分别传当天与历史各一条；同一条重复上传一次；到 iGP 网页端核对开始时间。
- 看日志：`对应平台客户端` 下载；时区修正行 `iGP时区修正+8h（按平台设置）` / `-8h`。**戒律：标记为 1 只代表 prefs 有值，不代表分支命中**，必须抓到目标分支专属日志行才算走过。
- 通过判据：当天与历史活动在 iGP 网页端显示的开始时间都等于采集时间（偏差 ≤1 分钟）；同一条重复上传不再次平移（幂等，不叠加成 +16h）；时间偏整 8h / 16h 为失败。

### 链路 ④ 启动横幅 / 登录态检测

- 操作：冷启动 App；遍历底部各 tab、打开关于页、时区设置页；观察登录卡片与统计卡；必要时点"一键登录检测"。
- 看日志：全局过滤运行时校验失败类异常（含资源清单损坏、启动期崩溃）；登录检测 `登录检测完成`、`登录有效`、`登录失效`、`token将过期`。
- 通过判据：启动不闪退；横幅/首页/各 tab/关于页/时区页正常 inflate；无上述异常堆栈；版本号三处一致。

### 链路 ⑤ 后台 Worker 与前台 Service 两条链路

- 操作：分别触发 (a) 后台任务（WorkManager）；(b) 前台任务（DATA_SYNC 前台服务），各跑一次批量/任务同步。
- 通过判据：两条链路结果与前台批量一致：下载/上传计数正确、pending 单列、不重复上传。注意迈金刷新链在后台任务上直调、无刷新包裹，属既有缺口。

### 模拟器取证做法

- 抓日志：先扩日志缓冲、清空历史日志，再后台持续落盘；复现后从文件筛 `TAG:` 关键行。
- 截图：先在设备端落盘再导出到本机；**禁止**用 命令行输出重定向直接写 PNG（重定向会得到体积正常但编码损坏的文件）。
- 本地调试设备起不来：先确认设备已被识别；启动参数落盘 stdout/stderr 再读；报错提示 SDK 根与镜像目录不匹配时，优先把镜像目录挂到调试设备认定的 SDK 根，不改启动配置。

## 三、高频坑位清单 T1–T23

> 每条：现象 — 根因 — 防范一句话。

### T1 分页参数 body/query 契约错位（服务端静默忽略，恒返回第 1 页）

- **现象**：单条下载正常，但批量列表永远只取同一批旧记录；"跳过 N 条"无效；数量填大仍只处理默认条数。
- **根因**：迈金 OTM 把 `page`/`limit` 塞进 JSON body，服务端静默忽略、`current_page` 恒为 1，query string 才生效；iGPSPORT 上层把"跳过"条数直接当 `pageNo`，无 `skip/size+1` 换算，跳过=0 → `pageNo=0` → `code=1003` 空响应。
- **防范**：直连对照四连（page=0 / page=1 / 末页 / query 版 page=2），只读 `current_page`、`total_pages`、首条时间戳与条数；页码归一化 `pageNo=(skip/size)+1` 且 ≥1；必须验证第 2 页与第 1 页不重叠。服务端对错误参数常静默忽略（仍返回 200 和完整一页），别误判成数据陈旧。
- **置信度**：迈金"只认 query"服务端行为待真机/抓包复核；iGP `pageNo=0` 业务错误码为直连实测。

### T2 时区标记不生效、双轨叠加 ±16h、字段形态混用与锚点法

- **现象**：同步后活动开始时间偏早/晚整 8 小时，极端样本 16 小时；当天与历史表现不一致；设置开关已开但日志零次命中修正分支。
- **根因**：①标记开着 ≠ 分支命中；②目标文件缺 `local_timestamp`，"两字段相等"条件永不成立；③下载端归一化、上传端 GPX 回写、iGP 专用偏移三套逻辑并存叠加；④当天/历史键名对调；⑤人工勾选 prefs 布尔不可靠。
- **防范**：用锚点法（见 `timezone.md`）替代字段法；两个平移逻辑不能同时跑，按来源分流而非追加调用；下载端已归一化的文件上传端开关保持"不调整"；验证看目标平台网页端时间。
- **置信度**：键名对调、−16h 路径已字节码基线证实；各平台网页端取 UTC 还是 local 字段待真机样本确认。

### T3 token 刷新与回写（迈金被动刷新一次、refreshToken 不回写、401/403 判定）

- **现象**：迈金每当有新活动需拉取时，本地登录态不可用，必须先重登一次；无新数据时列表返回空、看起来正常。
- **根因**：除启动检测一处 `<1h` 预检外，列表/下载/上传前均无主动刷新；401 后仅按文案子串匹配（"过期"/"401"）刷新一次；刷新只回写 access_token，从不回写可能轮换的新 refreshToken；上传链路无刷新、无重放。早期版本曾把 403 也并入重登分支，非鉴权 403 被误报成"请重新登录"。
- **防范**：刷新响应带回新 refreshToken 必须回写（空则保留旧值）；拉列表前做与启动检测同构的 `<1h` exp 预检；日志同时记录 HTTP 码与响应 message，区分"refresh 被拒（需重登）"与"网络错误（可重试）"；后台 Worker/Service 两条链路要单独补落点。
- **置信度**：R1（被动不完整、不回写）已证实；服务端是否轮换 refreshToken、是否作废旧 token 待真机抓包。

### T4 prefs 路径 / uid 写错导致账号态被清空

- **现象**：root 改设备 SharedPreferences 后整个账号态被清空、解析失败；或凭证读不到、登录态全丢。
- **根因**：凭证库是 `凭证库.xml`，平台时区开关库是 `开关库.xml`；文件名/键名写错读到空库；文件属主 uid 写错会让 SharedPreferences 解析失败、整个账号态被清空。
- **防范**：改 prefs SOP：先停止应用进程 → 改内容 → 属主保持应用真实 uid → 再启动；改前备份；新增凭证键先在本地状态层键表登记。
- **置信度**：已证实；具体 uid 随设备/安装变化，以实测包属主信息为准。

### T5 二进制产物被 命令行重定向写坏（截图/安装包体积正常但编码损坏）

- **现象**：出包安装包/类字节码或截图 PNG 体积正常，但编码损坏：截图读图报"媒体类型不支持"；安装包/类字节码无法解析或安装失败。
- **根因**：PowerShell 5.1 用 `>` 重定向写二进制（类字节码/安装包/PNG），文本编码层把字节流改写损坏；设备端截图经输出重定向取回同此坑。
- **防范**：二进制走打包/对齐/签名工具自身输出与设备端导出通道，不用 命令行重定向接二进制流；截图先落设备再导出；文本日志以 UTF-8 写文件。
- **置信度**：已证实。

### T6 巨型方法内联新类导致运行时校验失败；新类走备用类槽位注入

- **现象**：往巨型方法中间插代码、内联新类后，打包通过但装机启动/进页面闪退，日志抛运行时校验失败。
- **根因**：运行时做寄存器类型流校验，巨型方法中间插入代码改变类型流即触发运行时校验失败；打包通过 ≠ 运行时校验通过，这类失败只有真机/模拟器启动才暴露。
- **防范**：新逻辑封装独立静态方法，在合成小方法里调用；新增 UI 代码追加到方法末尾或独立类；新类走备用类槽位注入链；改完必须冷启动冒烟。
- **置信度**：已证实。

### T7 二进制资源清单字符串池禁止手改

- **现象**：手改二进制资源清单文案后装机，页面加载即闪退，报资源清单损坏。
- **根因**：手工重算字符串偏移、长度前缀、chunkSize、对齐，结构与二进制资源清单规范不符。
- **防范**：优先改源 XML 让打包工具重编；必须改二进制文案时做等长字节替换；禁止手工重建资源清单字符串池；资源 ID 新增检查源 XML 避免同名 id 冲突。
- **置信度**：已证实。

### T8 构建缓存静默复用旧字节码（"改了没生效"误判）

- **现象**：改完重打包装机，行为与改动前完全一样，看起来"改了没生效"。
- **根因**：打包工具增量编译复用构建目录缓存，未清缓存时静默复用旧字节码，改动根本没编进类字节码。
- **防范**：重打包前清构建目录全量重编；构建目录是可再生缓存可删，字节码/资源/资产源文件不可删。
- **置信度**：已证实。

### T9 kp_ 他人记录 403「不能下载他人运动记录」（独立问题，非客户端回归）

- **现象**：`kp_` 前缀记录下载失败，容易和全量失败的常量回归混在一起。
- **根因**：Keep 导入记录在 iGP 侧被标记归属他人，服务端拒绝下发；真实 token 直连返回 403 `{"code":1002,...}`，同账号普通记录返回 200 + OSS 直链。不是客户端回归、不是 token/网络问题。
- **防范**：403/code=1002 原文透出，按"无权限"跳过，不记为失败；不要从文件名 `kp_` 反推命名污染；即使分发链修好，这条记录仍会真实 403。
- **置信度**：已证实（直连 403 响应体）；记录归属变更的服务端成因未核实。

### T10 UploadResult pending 导致「显示成功但平台没数据」

- **现象**：报告里某条记为成功（✅ 或 🕐 待确认），但目标平台网页端查不到活动；下次同步本端直接跳过，不再重传。
- **根因**：异步平台"已提交、后台入库"状态被压成 `success=true / pending=false`；拿到 success 就立即写同步记忆键，平台侧异步失败后永久跳过。全仓仅 Outbase 按文案显式置 pending；iGP 异步分支与迈金语义上是后台异步，却都编码成 success/pending=false。pending 分支本身不写记忆键，但仍把单条计入成功合计。
- **防范**：异步入库平台等一下再查平台；上传判定别只用"data 非空"或"HTTP 200"；回 ACK 的结果同样打 pending，pending 单列"待确认"桶；二次确认队列延迟 15–30 分钟回查列表/详情，命中再补写记忆键。
- **置信度**：构造点/读取点/记忆键写入位置已证实；平台侧异步失败后未落库的后果表现待实测账号验证。

### T11 死代码误改无效（几代时间修正器只有一套被引用）

- **现象**：怀疑某工具类是死代码；改了它行为完全没变化，难以察觉。
- **根因**：仓库留着多套同类工具类，只有一套被外部引用；其余外部引用 0 命中（含反射形式）。
- **防范**：接手先判定生效源，顺调用链从 UI 入口/主循环走到目标方法；按类型描述符全树统计外部引用，剔除自身与内部类；死代码保留不动、登记待确认后清理；不要凭印象复活已删除/已回退逻辑。
- **置信度**：已证实（全树扫描）。

### T12 改错基线：两套字节码基线不同步 + 源码镜像过期

- **现象**：照另一套源码镜像改会把后加功能改丢；照维护基线改却拿官方字节码基线重打包，出现"改了但没生效"。
- **根因**：项目是"官方安装包反编译 + 补丁"流水线；另一套源码镜像停在旧版本，缺后加功能；维护基线快照与官方字节码基线在版本号、佳明分支等多处实质不同。
- **防范**：改动一律以官方字节码基线为准，改完再回写快照；先确认改的是重打包流水线实际读取的那一份；不要从官方基准基线重新派生补丁（会丢已验证补丁）。
- **置信度**：已证实（逐处复核）。

### T13 中文文案 `\uXXXX` 转义，直接 grep 0 命中假象

- **现象**：全树搜中文日志文案逐字 grep 0 命中，误判"代码里没有这个字符串"。
- **根因**：字节码基线里所有非 ASCII 字符都以 `\uXXXX` 转义存储。
- **防范**：把目标文案逐字转 `\uXXXX` 拼接再全树 SimpleMatch；或用按行解码后匹配的脚本；不要凭 grep 0 命中就下"无此逻辑"结论。
- **置信度**：已证实。

### T14 版本号多处手工维护，本地状态层不读 BuildConfig

- **现象**：关于页显示新版本，但 banner / 更新弹窗 / UA 仍自称旧版本号；更新检查永远误报有新版本或反之。
- **根因**：版本号散在多处手工维护，`本地状态层` 不回读 `BuildConfig.VERSION_NAME`；硬编码基线低于线上最新 Release 时比较恒为"检测到新版本"。
- **防范**：发版前按对齐点清单逐项核对；根治是让本地状态层改读 BuildConfig，版本号只在一处维护。
- **置信度**：已证实。

### T15 文档自述 / release notes 与字节码基线相反，以字节码基线为准

- **现象**：导览/README/修改说明写的分支方向与实际字节码基线相反，照着文档改会带反方向。
- **根因**：已记录两处冲突（行者 normalizer 方向；README 称迈金刷新已修复但实测链仍不完整）。
- **防范**：定位结论必须能回落到 文件:方法:行号；置信度三档分开标；文档自述仅作线索，冲突未澄清前不按文档结论动手。
- **置信度**：方向冲突已证实；normalize 两字段精确语义待真机样本确认。

### T16 403 分支维护基线缺失，从维护基线重打包会丢 403 识别

- **现象**：从维护基线重打包后，服务端返 403 不再识别为登录失效、不触发重试，退回旧文案。
- **根因**：维护基线比官方基线少 403 的 HTTP 层与 body code 层判定指令；被动重试匹配串只含"过期"/"401"，不含"403"。
- **防范**：重打包前核对维护基线与官方基线的分支完整性；403 回填到既有标签，不新增标签；不要把调用方匹配串扩成"403"。
- **置信度**：已证实（三套基线行号对比）。

### T17 寄存器槽位 liveness：字符串槽位与长度槽位必须分离；入参槽位不当临时

- **现象**：照草稿写回写逻辑后，新 refreshToken 永远存不进去，看起来改了其实没改。
- **根因**：调用返回值取字符串后 `length()` 覆盖同一寄存器槽位，字段写入存进去的是默认空串；合成访问器里的入参槽位不能当临时用。
- **防范**：字符串寄存器与长度寄存器必须是两个不同寄存器；新值非空才写字段，空则保留上一次值；临时值只用死亡槽位，不占入参槽位；扩槽位声明前全方法扫描无裸高号槽位硬编码。
- **置信度**：已证实（寄存器引用计数实测）。

### T18 监听器方法名 / 跨类 private 调用签名坑（运行时校验失败）

- **现象**：点弹窗确认按钮闪退（跨类访问受限）；或抽象方法未实现闪退（运行时校验失败）。
- **根因**：lambda 类跨类调用宿主类 private 静态方法触发访问受限；监听器接口方法名写错（如把 `onClick(DialogInterface,int)` 写成 `onItemClick`）触发运行时校验失败。
- **防范**：跨类调用的宿主静态方法改 public；监听器按接口签名写方法名与参数；新增 lambda/监听器后冷启动 + 点一遍弹窗按钮冒烟。
- **置信度**：已证实（历史修复记录）。

### T19 主类加载槽位方法数逼近 65,535 上限，新类必须落备用槽位

- **现象**：继续把新方法/新类堆进主类加载槽位，打包/类加载阶段出问题；主槽位类型数超 65536。
- **根因**：单类加载槽位 `method_ids` 硬上限 65,535；主槽位余量不足 2,000 方法引用。
- **防范**：新类落到独立备用类槽位（惯例备用槽位编号，避开现有 1–5）；不在主槽位继续堆新方法；注入后确认重打包纳入新槽位、装机类可加载。
- **置信度**：已证实。

### T20 启动检测串行 300ms 触发风控；「10 枚上限」属 Wahoo 非佳明

- **现象**：冷启动后登录卡片逐个校验，密集请求易触发佳明 429 账号风控；排查时把 Wahoo 令牌额度错记到佳明头上。
- **根因**：启动检测对已登录平台串行发真实校验请求，条间固定 300ms；佳明对短时间频繁登录临时限流 429。"10 枚未撤销令牌上限"是 Wahoo，不是佳明；佳明侧风险是 429 账号级风控。佳明明文直登仅 佳明中国区。
- **防范**：风控敏感平台只调大间隔、不整段跳过；不得把 CN 明文兜底放开到 COM；不要复活已删的 `本地状态层`；调试时别反复跑启动检测。
- **置信度**：已证实（分支判断/间隔常量/调用链实测）；风控冷却时长为服务端行为。

### T21 手写 FIT 解析器：dev 字段位误读导致位置错位

- **现象**：自写 FIT 解析器定位 activity 消息静默返回 null，或字段解析错位。
- **根因**：开发者字段并非总存在：必须按 record header 的 bit5（0x20）判断，该位为 0 时没有 dev count 字节；误读会把后续字段位置全部错开。
- **防范**：解析前先判 bit5 决定是否读 dev count；`findActivity` 找不到时兜底原样返回，不抛错中断主流程；FIT 头长度取 `header[0] & 0x0F`；解析异常 Throwable 兜底原样返回。
- **置信度**：已证实（历史踩坑记录）。

### T22 模拟器取证与本地调试设备启动诊断（环境坑）

- **现象**：本地调试设备启动后无设备、进程随即消失；或抓不到日志、截图损坏。
- **根因**：不重定向启动时进程秒退且 stdout/stderr 全丢；启动配置相对路径按模拟器认定的 SDK 根解析，SDK 装到子目录时报 SDK 根/系统路径不匹配；日志缓冲默认偏小；截图走输出重定向会损坏。
- **防范**：启动参数落盘 stdout/stderr 再读错误日志；SDK 根与镜像目录不匹配时优先挂接镜像目录，不改启动配置；抓日志先扩缓冲、清空再后台落盘；截图先落设备再导出。
- **置信度**：已证实（本机模拟器）。

### T23 列表字段名缺口：`rideDistance` 未解析导致 0.0km（侧线独立问题）

- **现象**：记录中心活动显示 `(0.0km)`；与下载失败是两条独立问题，不影响下载字节。
- **根因**：iGP 列表返回距离字段名是 `rideDistance`（另有 `totalMovingTime`、点分 `startTime`），兜底链只查 `Distance` → `distance` → `sportDistance`，未读取 `rideDistance`；距离取空显示 0.0km。
- **防范**：解析新平台列表字段时先 dump 原始 JSON 键名再写兜底链；distance 兜底链追加 `rideDistance`，沿用既有换算；真机核对单位（米/千米）避免重复换算。
- **置信度**：字段名缺口已证实；-1.0→0.0 折算点待真机核对。
